# 0003. Бронь — SQL-функции в Postgres

**Статус:** принято, 23.11.2026

## Контекст

Нужно гарантировать, что одно место не продано дважды, в том числе когда тысячи людей бронируют одновременно. Варианты: распределённые блокировки в Redis, очередь заказов, транзакции Postgres.

## Решение

Источник истины — `event_seats` в Postgres. Статусы меняют только функции `hold_seats`, `cancel_order`, `confirm_payment`, `expire_holds` (`security definer`). Клиент вызывает их через `rpc`, напрямую в таблицы не пишет (RLS + гранты).

## Почему

- Атомарный `UPDATE … WHERE status = 'free'` с блокировкой строк решает гонку без дополнительной инфраструктуры.
- Postgres держит тысячи таких операций в секунду — больше, чем нужно Бишкеку.
- Логика рядом с данными: нельзя обойти, забыв проверку в каком-то API-роуте.

## Последствия

- Логику пишем на PL/pgSQL — тестируем на PGlite (`tests/db/booking.test.ts`).
- Конкурентность PGlite не проверяет — нужен нагрузочный тест k6 до первого горячего события.
